# Operations and public launch gates

## Long-text reflow checks

Long unbroken source URLs, names and references inherit `overflow-wrap:anywhere` so they can wrap without widening the page or losing text. Do not clip evidence or truncate an identifier to resolve overflow. Comparison/history tables retain their contained horizontal scrolling where needed.

After building, `node scripts/preview-reflow-qa.mjs` serves a labelled synthetic loopback-only fixture on port 8797. The helper denies API routes, has no identity/provider/database access, and generates assets only under ignored `.sites-runtime`, outside deployment output. Stop it after testing. This is a targeted reflow check, not a full WCAG or screen-reader audit.

## Boundaries

The hosted release is an owner-private development preview. `DATA_MODE=demo` returns researched preview records; `DATA_MODE=production` returns only database records with `state=published` and `demo=false`. Publishing records does not make the Site public. Do not change audience until the launch gates below pass. Robots and metadata block indexing throughout this initial release.

Production authentication is provided by Sites dispatch. `EDITOR_USER_IDS` must be a comma-separated allowlist of stable authenticated user IDs, configured server-side. The default empty allowlist denies everyone. Local sign-in simulates `local_seedy`, only for loopback development. Put `EDITOR_USER_IDS=local_seedy` in an ignored `.dev.vars` to test locally; never grant this mock ID a hosted editor role. Direct exposure of the Worker bypassing the identity-verifying dispatch is unsupported.

## Editorial workflow

Editorial/correction APIs match exact endpoint lengths and bounded ASCII identifier segments. Extra segments and unknown routes return404 without reading a body or consuming a quota. Recognized routes reject unsupported methods with405 and Allow. Editor authorization is checked first for every admin request, including invalid routes. Non-paginated reads and all writes reject query parameters; paginated reads accept only one state and one cursor, validate state against the queue and reject unknown/repeated/empty or syntactically invalid values. Scoped cursor decoding and bound SQL remain authoritative. Rejected routing/query requests do not create audit entries or consume rate limits.

API HEAD uses the same read validation/authorization and headers/status as GET, then returns an empty body. It never delegates to a write route. To verify the built Worker locally, serve it on127.0.0.1:8796 and run `node scripts/verify-api-boundaries.mjs head`; run post-extra, post-query and post-admin as separate optional arguments for individual invalid-request checks. The helper is fixed to loopback, has bounded request timeouts and never sends a real identity or valid correction. Its default combined run reports failures rather than retrying or accepting a503. Wrangler may restart between sequential local POST requests; inspect its explicit restart body and use fresh individual checks to distinguish this verification limitation. Production writes never gain automatic retries from this helper.

Editor access checks and provider evaluations have a 15-second browser deadline covering fetch and JSON parsing, immediate duplicate-request guards and cancellation on navigation. A valid bounded stable user ID is required before the editor workspace renders; every server endpoint independently checks the actual role. A failed/malformed access response keeps the gate closed with an explicit retry. Browser validation never grants a hosted role.

Provider responses are validated and projected to known fields before display. Candidates remain unresolved GLOBAL evidence with empty prices and no photo; local-price or image payloads are rejected. Missing configuration is explicit. Failed or ambiguous evaluations clear prior results and warn that the attempt may still count toward the hourly quota/audit history. There is no automatic retry or catalogue import. Approved upstream rights, secure runtime credentials and live feasibility testing remain required.

After building, `node scripts/preview-editor-session-qa.mjs` runs a labelled loopback-only simulation: malformed access, valid synthetic identity on retry, missing provider configuration, malformed provider result, quota rejection, then empty-result recovery. It does not use or forward an identity, call a provider, or write a database. Its generated assets remain outside dist and are not deployed. Stop it after QA.

`POST /api/admin/imports`: sends `{record}` and an `Idempotency-Key` of 8–100 ASCII letters/digits/hyphens. Validated imports enter drafts. Exact brand/reference/dial/bracelet/material/size duplication is rejected. Inspect every source and claim before review.

`POST /api/admin/records/:id`: sends `{action,revision}`. A draft goes to review, then to published. `revise` accepts `{record}` only on drafts. `withdraw` returns published records to draft. `rollback` accepts `{targetRevision}` and restores a previous snapshot as a new draft, which requires review again. Every action is audited with actor, before/after values and time. Revision mismatch rejects concurrent writes. Public queries return published records only.

Price amounts are integer minor units; FX rates are decimal strings. Unknown specifications are null. Original prices require exact variant ID, type, source evidence, dates, country, ISO currency, condition, box/papers, seller type and tax status. Mark unknown tax basis literally. Retail requires a manufacturer or evidenced authorised source. Verified sales require completed-transaction evidence. Provider estimates require provider and assumptions. Removed listings cannot become verified sales.

Corrections use a bounded, validated, same-origin JSON endpoint and durable hourly rate limits. They enter pending moderation. Acceptance is not an automatic catalogue edit: apply the supported change through draft/review/publish, then mark resolved. Contact information is editor-only. The protected queues now page through all records, corrections and audit events in batches of 25. Corrections default to pending and can be filtered by moderation state; records can be filtered by publication state. Each exact record has its own paginated revision history, ordered by revision number. Select a prior revision and use the explicit restore button; selection alone never triggers rollback. Refresh or a successful mutation returns queues to their newest pages while keeping state filters. No data is deleted by pagination; a retention policy still requires an operating owner.


`GET /api/admin` checks the editor role and returns only its stable user ID. `GET /api/admin/queues/:queue` accepts records, corrections or audit; optional state and cursor parameters are validated. `GET /api/admin/revisions/:recordId` pages that record's revision metadata without returning all snapshot payloads. Queues return rows, pageSize, hasMore and nextCursor. Cursors are bounded navigation hints scoped to the queue/filter/record; they grant no permission. Every request independently enforces the editor allowlist. Invalid cursors/filters return 400, missing records or unknown queue routes 404, and database failures a sanitized 503. Responses are no-store/no-index.

Queues order timestamp then stable ID descending; revisions order revision number then ID. Equal timestamps do not hide or duplicate entries in a stable dataset. Concurrent edits can move a record to the newest page, so this is not a frozen database snapshot; refresh when reviewing active changes. Five additive indexes support filtered/unfiltered paging. Migrations do not modify watch values or source dates.
## Backup and restoration

Run the repeatable isolated rehearsal with Node 22.13+ and the locked dependencies:

```powershell
node scripts/rehearse-recovery.mjs
```

The script creates two disposable local D1 databases with a random test ID and synthetic rows across all 12 application tables. It exports schema and data separately, creates every referenced table before row insertion, and defers foreign-key checks during import. It encrypts the SQL using AES-256-GCM with a fresh ephemeral key, checks wrong-key/tamper rejection, restores the decrypted archive and compares every application row. Read-only SQLite checks validate the restored local database's integrity and foreign keys; D1's SQL authorizer does not expose integrity_check. It also verifies the source was unchanged. Temporary files and the rehearsal key are removed. This is a recovery test, **not a durable backup command or hosted recovery verification**.

The checked-in sanitized result is `docs/recovery-rehearsal.json`. To refresh it, pass `--report` followed by its absolute JSON path. The report contains counts/digests and check outcomes, never SQL, correction contacts or keys. Real backups must remain outside Git, encrypted and access-restricted; `/backups/` is ignored as an additional precaution. Durable encryption-key custody and recovery access still need an operating owner. Do not use the ephemeral rehearsal key for real backups.

For operator-managed D1 exports, use the installed Wrangler's documented `d1 export` flags; export does not accept `--persist-to`. Export schema/data separately and restore into a disposable database before any live recovery. Match the original migration/schema version. Never restore over the only live copy. Wrangler `--local` commands select local state only.
Hosted D1 is provisioned by Sites. Identify the actual hosted database and operator-managed backup facility before launch; local `--local` commands do not back up hosted data. Configure a daily encrypted backup/retention policy through the chosen host facilities, record an operator and rehearse restore. Scheduled hosted backups, monitoring alerts and the hosted restore rehearsal are **not configured** in this preview; no supplied operations account/budget exists.

## Protected system checks

Evidence-date validation accepts only real ISO calendar dates or explicitly zoned ISO timestamps, preserving original strings and up to nine fractional digits. It rejects silent calendar rollover, locale-dependent dates, missing licence checks and price checks earlier than their observations (including sub-millisecond differences). Public projection withholds invalid legacy evidence rather than guessing a replacement date. Freshness requires valid observation/check chronology and cannot fall back to an observation date when its check is missing. Provider update dates failing this contract remain null; no refresh or live integration is implied. Coverage reviews with invalid dates are omitted from request snapshots.

Health checks count impossible, missing or reversed observation/check timestamps as invalid rather than stale/fresh. Repair evidence through the protected review workflow after inspecting the original source; do not assign the current time merely to make an old record pass. Valid source, photo and price timestamps remain unchanged.

An allowlisted editor can run System checks in `/admin`, backed by read-only `GET /api/admin/health`. Missing/unauthorised identity gets 403, and unavailable database checks get a sanitized 503. It reports record counts, pending correction count/oldest date, published price freshness (30 days retail, 7 days other types) and hourly provider evaluation count. Archived prices are excluded; malformed/future check dates require review. At most 5000 observation rows are scanned, with an explicit partial-result warning above that limit. Only counts/configuration booleans are returned, never provider credentials, contacts or full audit payloads. The request check date does not refresh any catalogue source date.

These manual checks are not scheduled monitoring. Alerts remain unconfigured and hosted recovery remains unverified even when database checks pass. Research mode is explicitly flagged; published database rows are not a validation of data rights. Publishing/reviewing/withdrawing a record now preserves archived_research observation status throughout the workflow.

## Incidents and rollback

Historical evidence uses the same `historySeries` policy on the page and `GET /api/watches/:variantId/history`. Query parameters are optional `market=IN|AE|GLOBAL` (default IN), `type` from the six observation types (default official_retail), and one opaque `series` value copied from the response. Do not construct series IDs. The endpoint returns eligible series metadata and observations for one selected comparable series, or an explicit unavailable result. Unknown/repeated parameters return 400; an unknown selected series returns 404. The route is read-only and does not fetch a provider or refresh dates. Error responses expose no database details. Withdrawal/draft state, demo mode, missing history approval or insufficient evidence suppress history.

Source retention/display permission and per-observation history approval are separate from ordinary price publication. Review them through the protected draft/review/publish flow. Preserve original timestamps, conditions, tax/fee basis and provider assumptions. Never relabel a snapshot to create a trend. Conflicting same-time amounts are withheld; correct evidence through the editorial workflow. Historical points are not required to be current offers: their original/check dates remain visible and stock is never inferred. Global scope is an explicit separate selection and never becomes local data through market switching.

For isolated browser QA, after a production build run `node scripts/preview-history-qa.mjs` and open its printed loopback URL. It mounts the real history component with explicitly synthetic test fixtures from `tests/fixtures/history.mjs`; it never writes to D1, the catalogue, public assets or the deployed build. The fixed loopback server serves only its harness HTML/JS/CSS and must be stopped after testing. Its generated files stay under ignored `.sites-runtime/history-qa`. Do not treat its synthetic numbers or test permissions as market data or a real licence. Verify the production build contains no synthetic fixture identifiers before packaging.

Image delivery failures preserve the recorded source, licence and check date. A thumbnail may fall back only to the same approved photograph's local full-size derivative. No unrelated watch, original remote file or unapproved image is substituted. Full failure shows an unavailable panel; gallery enlargement is disabled until explicit retry succeeds. Retry resets the main image and thumbnails together. A different registered gallery photograph requires explicit selection. Coverage counts describe approved records, not current asset delivery health. Delivery retries do not refresh licence or source dates.

Withdraw an inaccurate record immediately through the protected editor control, retaining audit/history. Investigate the original evidence, stage a correction and re-review. A failed provider fetch never updates existing records or checked dates. Keep provider evaluation disabled if rights, quotas or upstream behaviour are uncertain.

For a UI/server regression, redeploy the last successful saved Sites version using its returned opaque version ID. Do not assume database migrations reverse with code rollback: schema changes are append-only, and failed deployments may already have applied migrations. Data rollback uses the record revision workflow; disaster recovery uses a separately verified backup.

### Saved-code recovery procedure

1. Read the current site access policy and saved versions. Preserve the existing audience. Record the starting saved version, its source commit, successful deployment and environment revision before any redeployment.
2. Select a previous successful saved artifact and compare its source with the current release, especially migrations, data contracts, hosting bindings and runtime configuration. Confirm compatibility with the current database and environment. A saved code version does not restore old data or old secrets. If compatibility is uncertain, diagnose or use a separately verified recovery procedure before redeploying it.
3. Use the native saved-version deployment operation for the existing audience. For a verified owner-private site, use `deploy_private_site_version` with the exact returned project/version IDs. Do not upload another version or reset/force-push Git to perform a hosted rollback. Do not change sharing or tunnel bindings during recovery.
4. If the operation is non-terminal, follow its returned deployment ID to a terminal status. For a failed or uncertain call, reconcile that deployment before retrying; never infer completion from the URL alone.
5. After success, reload representative pages and verify configuration, selected market, supported/unavailable prices/photos and original evidence dates. Record the native deployment result as the build identity; identical page text cannot prove which build is running. Do not submit real corrections or edit catalogue data merely for a smoke check.
6. In a rehearsal, restore the recorded starting version and repeat the smoke checks. In an incident, keep the compatible known-good release until the fix passes review and testing. Record results and any remaining database/environment recovery needs.

The first same-schema hosted rehearsal passed on 17 October 2026: saved version 38 → 37 → 38, with unchanged environment revision and dated unavailable Cartier evidence. See [deployment evidence](DEPLOYMENT-REHEARSAL.md). This does not complete hosted database restore or qualify all older versions for rollback.

## Correction response recovery

The public correction client enforces a15-second deadline through response JSON parsing, aborts on navigation and never automatically repeats a submission. Only a201 receipt matching the current UUID confirms storage and clears text. Unchanged normalized text keeps the same key across explicit retries within the mounted form. Private text/email and retry keys are not persisted to device storage. A timeout does not prove the server failed to commit; retry unchanged text to recover its existing durable receipt.

Malformed receipts/errors preserve text and show uncertainty. Server field errors require bounded known keys and string values; the browser displays its own fixed help wording instead of arbitrary server error content. Known quota, conflict, size and rejection responses have controlled messages. Field focus moves after the fieldset is enabled, with the error summary and field associations available. Reload/navigation loses an unconfirmed in-memory draft, so retain a copy first if instructed to reload.

For repeatable UI QA after building, run `node scripts/preview-correction-recovery-qa.mjs`. Its labelled loopback-only simulation rejects a malformed error, returns a safe field error and then confirms the same UUID; unchanged body/key reuse is enforced. It stores no submission and forwards nothing. Generated QA assets remain outside dist and are not deployed. Stop it after testing.

Public pages, their serialized client props, metadata/sitemap reads and public watch APIs receive only the server-projected catalogue. The protected editorial queues and revision snapshots retain full stored records and still enforce the editor role. A record with invalid essential identity/source evidence is withheld; invalid optional claims remain unavailable. Malformed stored JSON is skipped without leaking its payload. This read boundary performs no database writes and does not replace draft/review/publication or source-rights review.

Unknown, repeated or invalid parameters return 400. The response contains `observations` for current eligible published rows and a separate `archivedResearch` list; archives never become current values. Every returned row has original scope/currency/type/dates and a public source object with its URL, check date and retailer-authorisation evidence where recorded. Global currency is null at response level because each original row keeps its own currency. No conversion or range is inferred. This replaces the earlier unfiltered bare price-array response; consumers must select the appropriate list and retain archive labels. Public catalogue queries remain no-store/no-index through response policy.

Search suggestions are generated locally from the catalogue already loaded for the page; typing does not call a provider or send an analytics event. They show at most six distinct configurations with their existing reference, dial, bracelet, material and size. Curated aliases are search aids only. Case, whitespace and common reference separators are normalized for matching; original reference text and variant IDs remain unchanged. Complete reference matches rank ahead of incidental model/alias text under relevance sorting. Catalogue suggestions respect its active filters, including original local retail eligibility. Missing prices remain excluded from price filters.

The search input retains focus while arrows choose a suggestion. Enter opens an explicitly selected configuration in the current market; Enter without selection performs the ordinary catalogue search. Escape closes suggestions without changing the query; Tab closes them and follows the normal form focus order. Pointer selection follows a normal exact-configuration link. No photographs or prices are inferred for suggestion rows. The ordinary GET form remains available without JavaScript; suggestions require hydration. Search text and suggestions are not persisted in browser storage by this feature.

Saved watches remain browser-local; no account or cloud save is implied. Market, favourites and comparison preferences are read independently so malformed data in one key does not block the others. Reads never rewrite device storage. Unknown saved catalogue IDs are retained with an unavailable-selection notice, rather than silently deleted or filled with guessed metadata. Supported selection IDs are deduplicated; comparisons accept at most three currently known configurations in selection order.

Storage access or quota failures return an explicit failure result. Save/clear messages do not claim persistence after a failed write; a persistent page notice explains that changes may be lost on navigation. Valid save changes synchronize across same-origin tabs through browser storage events. Unreadable updates do not replace an already loaded saved selection. ## Correction receipts and accessible validation

The public correction endpoint and client share field validation. A valid local page path may retain market=IN/AE; inputs are normalized and bounded, email remains optional, and field errors return without publishing anything. Correction links now retain the exact market context. Inline errors are associated with their fields and summarized in an alert; initial invalid submission focuses the first invalid field. The form is disabled during a pending request and prevents concurrent client submissions.

The form generates a UUIDv4 Idempotency-Key for each normalized payload. Within the loaded form, a retry of unchanged text reuses that key; changing the text creates a new key. Keys and correction text are not persisted in browser storage. A successful receipt requires HTTP 201 and the matching identifier. Only then are the fields cleared; the page context remains. Timeout, disconnected fetch or unreadable/mismatched response reports an unconfirmed receipt and preserves the current form text. Do not refresh/navigate away if relying on that in-memory draft.

The database uses the key as the correction ID. Exact retries return the same receipt even after moderation. Reusing a key for different normalized text returns 409, and parallel inserts use the primary-key conflict guard so only one row is created. Receipt responses expose no contact details and are not a public correction lookup. Legacy clients may omit the header and receive a server-generated ID; their independently retried requests cannot be deduplicated. Anonymous submission never changes the published catalogue.

Durable hourly limits allow five new corrections per request IP and 30 total validated submission attempts (including receipt retries). Same-origin JSON, bounded request size, honeypot validation, protected moderation and no-store/no-index responses remain in place. Hosted dispatch must provide trustworthy network/identity headers. Editor provisioning, retention ownership and monitoring remain launch gates.

The main skip link now focuses main content. Mobile navigation names its controlled region; Escape from its trigger or links closes it, returning focus to the trigger when needed. These targeted checks do not constitute a complete WCAG audit.

Publication checks also scan the first 1000 published record payloads in the same order as the production catalogue, independent of DATA_MODE. They apply the public projection with production rights requirements and report only aggregate counts: checked, visible, withheld, unreadable JSON, rejected published price entries and rejected primary photos. Price/photo counts cover visible records only; an entirely withheld record is counted once at record level. More than 1000 rows triggers a catalogue-limit warning. Passing these checks does not establish publication permission or complete launch acceptance. Review the protected editorial queue to diagnose records; no private payload or reason text is returned by the check. Re-running clears the prior report so a failed request cannot leave an old success visible.

For local UI verification without editor credentials, run `node scripts/preview-publication-qa.mjs` after a build and open the printed loopback URL. It renders the actual component with a clearly labelled synthetic report, returns a simulated failure on the second check, and succeeds on retry. It does not change the real admin route or require an editor identity. Its temporary bundle is outside dist and is not deployed.

## Public catalogue query contract

GET /api/watches returns `{data: Watch[], pagination, mode}`. The data array is now paginated: callers must follow `pagination.nextPage` rather than assume the first response contains the full catalogue. Defaults: market=IN, page=1, pageSize=24. Page size is1–50 and page is1–1000. `pagination` reports page, pageSize, total, totalPages, hasPrevious, hasNext, previousPage, nextPage, market and currency. Total describes the loaded public catalogue (at most1000 approved records), not the wider market. An out-of-range valid page returns an empty array and no next page; previousPage points to an available prior page when one exists. Pagination is not a database snapshot: publication changes between requests can change membership.

Supported filters are q (up to200 characters), brand/material/movement/collection (up to120 each), size (10–70mm, up to2 decimal places), maxPrice (positive whole major-currency units whose minor-unit equivalent is a safe integer), market (IN/AE), and sort (relevance/name/price). Omit unused filters. Blank, unknown, repeated, invalid or out-of-bound parameters return400 without echoing their contents. Malformed list/detail queries are rejected before catalogue reads. Search ranking, exact matching and current local official-retail eligibility remain shared with the UI. Missing retail never qualifies under maxPrice, and price sort keeps unavailable prices last. No conversion creates a local observation.

Example: `/api/watches?brand=Cartier&market=AE&maxPrice=20000&sort=price&pageSize=5&page=1`. The data retains each watch's original source/price metadata, including other markets; market controls search eligibility and sorting. Use the separate `/api/watches/:id/prices?market=AE` endpoint for a market-scoped price response. Detail GET accepts only optional market=IN/AE; prices/history retain their dedicated validated contracts. Every public API success/error response uses no-store and noindex. Production ordering includes the variant ID as a tie-breaker for otherwise equal brand/reference rows; system checks scan that same ordering. No data or check dates are written by a read.

## Safe editorial failures

Public correction and protected editorial writes require a JSON object and valid UTF-8, with a150000-byte body limit enforced against both advertised and streamed size. Malformed JSON/encoding/primitive roots return safe400 errors; oversized bodies return413 and excess streams are cancelled. Media type checks reject lookalikes such as application/jsonx. Imported/revised records retain validation gates but expose a fixed import-format/source-rights message on validation failure, not raw exceptions. Invalid provider references are rejected before quota/storage access.

Unexpected failures return a fixed503 with no SQL, file path, payload, token or original exception text. Database constraint failures return a fixed409 conflict message; intentional request errors retain their explicit statuses. A service failure does not prove a mutation failed before committing. Retry public corrections with the same idempotency receipt key; refresh editorial revisions before repeating a mutation and reuse import idempotency keys. Do not replace a failed/uncertain request with a fresh key simply to bypass the receipt check. Protected health/queue checks retain their existing sanitized responses. This is error disclosure hardening, not hosted monitoring or a live role-provisioning test.

## Public routes and catalogue outages

Record, correction, audit and revision queue reads have a15-second deadline covering fetch and JSON parsing. ## Confirmed editorial writes

Import, record-transition/revision/rollback and correction-moderation writes have a15-second deadline including JSON parsing, unmount cancellation and an immediate in-flight write guard. They are never automatically repeated. An import clears its draft only after a matching created-record response or matching idempotent replay; record operations must confirm the same ID, expected state and next revision; moderation must confirm the requested state. Ambiguous2xx, failed parsing, transport failures or timeouts keep the draft and warn that the outcome is uncertain. Check queues/audit history before repeating a revision or publication. A cancelled browser request does not undo an already committed server operation.

Within the mounted workspace, unchanged serialized import content reuses its idempotency key after an unconfirmed response; changed content starts a new attempt. The key is cleared after confirmed import. Neither private record text nor its retry key is persisted to device storage by this feature. The JSON editor is disabled during pending operations. Successful unrelated queue/moderation actions preserve the current draft; only confirmed import or the matching draft revision clears it. # Conflicting retail summaries

If newest retail observations disagree, cards, regional summaries and coverage show the retail summary as unavailable. Price filters exclude it. Details and comparison retain the individual sourced amounts and dates with an explicit conflict explanation. Resolve the discrepancy through the protected editorial review workflow; do not change timestamps merely to choose a preferred price. The summary compares the newest observation time, not the newest check time. Matching amounts also require matching currency, condition, box/papers, tax status and retail basis. Source observation counts remain evidence counts and do not imply an available summary.

## Asking-range review

Ranges require five distinct eligible local comparable offers. Converted amounts and non-local currencies cannot contribute. Within each comparable group, each listing contributes its newest eligible observation; conflicting newest amounts or tax bases with the same timestamp are withheld. Dates are compared at millisecond precision. The UI reports duplicate observations, conflicting listings and the actual observation window. Original evidence is retained separately. These calculations do not verify availability; source integrations must maintain offer removals and exclusions rather than import obsolete offers as live listings.

Outliers outside the quartiles by more than 1.5 times the interquartile range are flagged for editorial review. They remain in the range, median and count until an explicit reviewed exclusion. The expandable evidence shows original amount, currency, observation/check dates, tax status and source. A statistical flag does not establish an erroneous price or a completed sale. No real asking dataset is connected in the research preview; unsupported ranges remain unavailable.

## Client asset-size regression gate

The default release build runs the framework build, publication scan and `scripts/check-asset-budgets.mjs` in order; any failed or incomplete step blocks release. Standalone command: `npm run check:assets` after a complete build. The read-only scan measures all emitted public JavaScript and CSS using gzip level 6 and checks display-photo file sizes in `watch-photos`. It rejects missing JavaScript/CSS, malformed limits/measurements, symbolic links and oversized/unbounded scans. It does not alter assets or evidence.

Limits in `scripts/release-budgets.json` use bytes: total JavaScript gzip 180000, individual JavaScript gzip 70000, total CSS gzip 12000, individual display photograph 250000. These are project regression limits based on the measured initial build, not industry performance guarantees. When a limit fails, inspect the named public asset and remove unused code or optimise the approved display derivative. Preserve original/licence records and exact-configuration evidence. Increase a limit only with a documented reason and a fresh performance review; do not bypass the build gate.

All client chunks are counted, including deferred chunks, so the total is not an initial-route download estimate. Actual host compression, caching and requests may differ. Original downloads under `watch-photos/originals` and other assets are excluded; the gate does not measure them. Image rights and matching checks remain separate. This is not a network test, Lighthouse score, field LCP/INP/CLS result or accessibility certification. Public-environment lab checks and real-user performance measurements remain required.
